上线前的 API 集成检查

把故障、隐私与恢复能力变成上线前可以验证的条件。

保护完整的数据路径

密钥保存在服务端，开发与生产凭据分开，日志去除敏感内容。发送机密信息前明确保留、删除、处理地区和分包方。请求格式兼容，不代表数据处理方式满足你的要求。

发布记录应写明数据负责人、获准发送的数据类别、密钥负责人和轮换步骤。实际撤销一个测试密钥，并确认它不能再授权新请求，才能认为密钥管理通过验收。

验证有边界的失败处理

用安全输入测试超时、限流、异常响应和流式中断。设置递增等待、有限重试及整体截止时间，避免重复请求导致付款等不可逆外部操作被再次执行。

预先写明通过条件：没有无限重试、没有重复副作用、调用方收到明确且可恢复的错误。确认取消操作停止了本地工作，再单独调查供应商是否仍在处理或计费。

观测直到任务完成

在自己的负载下测量成功完成率、首个有效响应、总耗时和计费。保留关联标识但不暴露提示词，将供应商故障与本地解析、网络错误分开，保证记录能用于定位问题。

运行记录至少包含时间、发布版本、路由、模型、状态、耗时、用量和告警负责人。按服务目标选择阈值，并发送测试告警，确认有权减少流量或关闭集成的人确实收到。

演练恢复并完成签收

备用服务应支持所需功能与获准的数据处理地区，而不只是接口相似。用非敏感数据切换并检查输出兼容性，记录回退、凭据替换、消费控制和支持升级路径。

为每个未解决问题指定负责人，关键检查不通过就阻止上线。保存带日期的验收结果，演练恢复主路由；服务商、模型或应用发生重要变化后，重新执行受影响的检查。
